1

O ESQUELETO, PALAVRA POR PALAVRA

Você vai escrever estas seis linhas centenas de vezes. Vale entender cada palavra uma vez, em vez de copiar para sempre.
public class Main {
    public static void main(String[] args) {
        System.out.println("Ola");
    } // end main
} // end class Main
PalavraO que ela faz de verdade
public (na classe)Deixa a classe visível de qualquer lugar. Se ela é public, o arquivo é obrigado a se chamar Main.java — mesmo nome, mesma caixa.
class MainEm Java não existe função solta: todo código mora dentro de uma classe.
public (no main)A JVM está fora da sua classe. Se o método não for público, ela não enxerga e não chama.
staticO método pertence à classe, não a um objeto. É o que permite a JVM chamá-lo sem criar um objeto antes — ela não teria como saber quais argumentos passar para o construtor.
voidNão devolve nada.
mainO nome exato que a JVM procura para começar. Escreveu Main ou principal, o programa compila e não roda.
String[] argsOs argumentos da linha de comando. Quase sempre vazio — mas a assinatura tem que estar exata, senão a JVM não reconhece como ponto de entrada.

A regra do nome do arquivo não é burocracia. Ela existe para o compilador achar a classe sem varrer o projeto inteiro. E ela morde de um jeito específico:

Classe public → o arquivo tem que ter o nome dela.
Classe sem public → o arquivo pode ter qualquer nome.

Por isso o beecrowd exige public class Main: o arquivo que ele cria se chama Main.java. E é por isso que, em ferramentas online que salvam o seu código com outro nome, você vê o erro class Main is public, should be declared in a file named Main.java.

Compilar e rodar:

javac Main.java   # gera Main.class (bytecode)
java Main         # roda — sem .java e sem .class no fim

Repare na assimetria: você compila o arquivo (com extensão) e executa a classe (sem extensão). Escrever java Main.class é o erro clássico da primeira semana.

2

IMPORTS E PACOTES

Um import não carrega nada. Ele é só um apelido: permite escrever o nome curto da classe em vez do nome completo.

A prova é que dá para viver sem ele — basta escrever o nome completo:

// sem import nenhum, usando o nome completo:
java.util.Scanner entrada = new java.util.Scanner(System.in);

// com import, o mesmo código fica legível:
import java.util.Scanner;
Scanner entrada = new Scanner(System.in);

Três consequências disso, que resolvem quase toda dúvida sobre imports:

  1. Não custa desempenho. É resolvido na compilação. Não entra nada a mais no bytecode e o programa não fica mais lento nem maior.
  2. Import a mais não atrapalha. Se você importa algo que não usa, é linha morta — nem erro, nem aviso relevante.
  3. Import não cria classe. Se a classe não existe no seu projeto, nenhum import vai inventá-la.

O que já vem sem pedir

O pacote java.lang é importado automaticamente. É por isso que isto funciona numa classe vazia, sem nenhum import:

Vem de graça (java.lang)Exemplos
Texto e númerosString, Integer, Double, Character, StringBuilder
Sistema e matemáticaSystem, Math, Object
Exceções comunsException, ArithmeticException, NullPointerException, ArrayIndexOutOfBoundsException, NumberFormatException

O que você precisa pedir

ImportO que trazQuando
java.util.*Scanner, Arrays, ArrayList, LinkedList, Stack, Queue, HashMap, Comparator, LocalePraticamente sempre
java.io.*BufferedReader, InputStreamReader, PrintWriter, IOExceptionQuando o Scanner for lento demais
java.math.*BigInteger, BigDecimalNúmeros além de 64 bits
java.util.stream.*Stream, CollectorsSe usar programação funcional
A pegadinha do asterisco: o * não é recursivo. import java.util.*; traz java.util.List, mas não traz java.util.stream.Collectors — subpacote é outro pacote. O nome engana porque stream parece estar “dentro” de util: está no nome, não no pacote.

Importar ≠ ter o arquivo

Classes do JDK você importa. Classes que alguém escreveu — sua, ou do professor — não se importam do nada: o arquivo .java precisa existir. É o caso da MyIO usada na disciplina:

SituaçãoO que fazer
Scanner, Math, ArrayListVêm com o Java. Basta o import (ou nada, se for java.lang).
MyIO e outras classes do professorColocar o arquivo MyIO.java na mesma pasta. Sem pacote declarado, chama direto, sem importar nada.

Se aparecer cannot find symbol: class MyIO, o problema é arquivo faltando, não import faltando. Nenhuma linha de import conserta isso.

O molde que resolve o beecrowd:

import java.io.*;
import java.util.*;

Os dois juntos não colidem. Colisão de nomes acontece em casos como java.util.Date e java.sql.Date, onde o compilador acusa reference to Date is ambiguous e você precisa escrever o nome completo. Entre java.io e java.util isso não ocorre.

SAÍDA — E O LOCALE

Esta seção evita o erro que mais reprova código logicamente correto em juiz online.
ComandoO que faz
System.out.println(x)Imprime e pula linha.
System.out.print(x)Imprime e não pula linha.
System.out.printf(...)Imprime com formato — é o único que controla casas decimais.

O printf usa marcadores que são substituídos pelos valores, na ordem:

MarcadorServe paraExemplo
%dinteiroprintf("%d", 42) → 42
%freal (6 casas por padrão)printf("%f", 1.5) → 1.500000
%.2freal com 2 casasprintf("%.2f", 1.5) → 1.50
%stextoprintf("%s", "ola") → ola
%nquebra de linhapreferível ao \n
O erro nº 1 de quem começa: o println não arredonda. System.out.println(3.14159 * 2 * 2) imprime 12.56636, e o problema pedia 12.5664. Casa decimal só se controla com printf.

O Locale — a armadilha invisível

O Java formata número de acordo com a região do computador. Num sistema em português, a separação decimal é a vírgula:

System.out.printf("%.2f%n", 6.25);
// no seu PC em português:  6,25   ← o juiz recusa
// num PC em inglês:        6.25   ← o juiz aceita

// forçando ponto, sempre, em qualquer máquina:
System.out.printf(Locale.US, "%.2f%n", 6.25);
// sempre 6.25

É o pior tipo de bug: o programa está certo, a lógica está certa, e o resultado depende de onde ele roda. Se der wrong answer num problema com número decimal e você não achar erro nenhum, olhe a vírgula primeiro.

Locale está em java.util — se você já importou java.util.*, está resolvido.

Por que preferir %n a \n: o %n usa a quebra de linha do sistema, o \n é sempre o caractere Unix. Para o juiz os dois passam; é um bom hábito para quando você escrever arquivos.

ENTRADA — SCANNER SEM ARMADILHA

O Scanner lê da entrada padrão. Você cria um e vai pedindo os valores no tipo que precisa:

import java.util.*;

public class Main {
    public static void main(String[] args) {
        Scanner entrada = new Scanner(System.in);

        int n = entrada.nextInt();
        double x = entrada.nextDouble();
        String palavra = entrada.next();      // uma palavra só
        String linha = entrada.nextLine();     // a linha inteira

        entrada.close();
    } // end main
} // end class Main
A armadilha do nextLine depois do nextInt. O nextInt() lê o número e deixa a quebra de linha para trás. O nextLine() seguinte encontra esse resto e devolve uma string vazia, sem esperar você digitar nada.
int n = entrada.nextInt();
entrada.nextLine();                // consome o resto da linha
String nome = entrada.nextLine();   // agora sim lê o que você quer

É exatamente o mesmo problema do scanf com fgets em C — a causa é idêntica, sobra a quebra de linha no buffer.

Ler até acabar a entrada

Muito problema não diz quantos casos existem: você lê até o arquivo terminar. Os métodos hasNext… respondem se ainda há algo:

while (entrada.hasNextInt()) {
    int a = entrada.nextInt();
    int b = entrada.nextInt();
    System.out.println(a + b);
} // end while

Quando o Scanner não dá conta: ele é cômodo, porém lento. Passando de umas dezenas de milhares de valores, começa a dar time limit exceeded. A troca é o BufferedReader, que lê a linha inteira de uma vez:

import java.io.*;

public class Main {
    public static void main(String[] args) throws IOException {
        BufferedReader in = new BufferedReader(new InputStreamReader(System.in));
        int n = Integer.parseInt(in.readLine().trim());
    } // end main
} // end class Main

Repare no throws IOException: o readLine() pode falhar, e o compilador obriga você a tratar ou declarar. O Scanner não exige isso porque engole os erros de leitura internamente — é a única diferença prática entre os dois no começo.

TIPOS, LIMITES E CONVERSÃO

Em Java o tamanho de cada tipo é fixo, igual em qualquer máquina. Isso é diferente de C, onde int pode variar de compilador para compilador.
TipoBitsVai atéQuando usar
int32± 2.147.483.647 (~2,1 bilhões)O padrão para contar coisas
long64± 9.223.372.036.854.775.807 (~9,2 quintilhões)Somatórios grandes, fatoriais
double64~15 dígitos significativosTodo número real
float32~7 dígitosEvite — precisão baixa demais
char16um caractere UnicodeLetra isolada
boolean—true / falseNão é 0 nem 1: tipo separado
Estourar não dá erro. Passou do limite, o int dá a volta e vira negativo, calado. Integer.MAX_VALUE + 1 é -2147483648. Nada avisa — você só percebe pela resposta errada.

Regra prática: se o resultado pode passar de ~2 bilhões, use long. Um fatorial estoura int já no 13º termo, e Fibonacci por volta do 47º.

Divisão inteira — o erro silencioso

int a = 7, b = 2;

double errado = a / b;        // 3.0  — a conta virou inteira ANTES de virar double
double certo  = a / (double) b; // 3.5
double tambem = a / 2.0;      // 3.5  — basta um lado ser real

Note que double errado = a / b; não dá erro nem aviso: o Java faz a divisão inteira primeiro e só depois converte o 3 para 3.0. A conversão chega tarde demais.

Conversão: quando é automática e quando é na mão

DireçãoComoExemplo
Menor → maiorAutomática, nada a fazerlong x = 10; · double y = 5;
Maior → menorCast obrigatório, e você perde informaçãoint n = (int) 3.9; → 3 (trunca, não arredonda)
Texto → númeroInteger.parseInt / Double.parseDoubleint n = Integer.parseInt("42");
Número → textoConcatenar com "" ou String.valueOfString s = "" + 42;
(int) 3.9 dá 3, e (int) -3.9 dá -3. O cast corta a parte decimal, ele não arredonda. Para arredondar de verdade existe Math.round.

E sobre double: ele é binário, então 0.1 + 0.2 não dá exatamente 0.3. Por isso nunca se compara real com ==; compara-se a diferença contra uma margem pequena.

STRING — ==, EQUALS E STRINGBUILDER

Em Java, String é objeto, não vetor de char. Isso muda duas coisas que pegam todo mundo.

1. Comparar com == compara o endereço

String a = new String("ola");
String b = new String("ola");

a == b        // false — são dois objetos diferentes
a.equals(b)   // true  — o conteúdo é o mesmo

O == pergunta “é o mesmo objeto?”. O equals pergunta “tem o mesmo conteúdo?”. Para texto você quase sempre quer o segundo.

Por que o erro demora a aparecer: com literais, String a = "ola"; String b = "ola"; o == devolve true, porque o Java reaproveita o mesmo objeto. Aí você acha que funciona — até o texto vir de uma leitura, e passar a dar false sem explicação. Use equals desde o começo.

2. String é imutável — e isso tem custo

Nenhuma operação altera uma String: cada uma cria outra. Então concatenar dentro de laço faz o programa copiar tudo de novo a cada volta:

// O(n²) — a cada volta aloca um objeto novo e copia o texto inteiro
String r = "";
for (int i = 0; i < n; i++) {
    r += letra[i];
}

// O(n) — o StringBuilder é um buffer que cresce
StringBuilder sb = new StringBuilder();
for (int i = 0; i < n; i++) {
    sb.append(letra[i]);
}
String r2 = sb.toString();

Com 100 caracteres ninguém percebe. Com 100 mil, o primeiro trava e o segundo termina na hora. Esse é o erro clássico de quem vem de C, porque em C você escreve direto no vetor e o custo simplesmente não existe.

Métodos que você vai usar sempre:

MétodoO que faz
s.length()Tamanho — com parênteses (em array é .length sem)
s.charAt(i)Caractere da posição i
s.substring(a, b)Trecho de a até b-1
s.split(" ")Quebra em vetor de palavras
s.trim()Remove espaços das pontas
s.toCharArray()Converte para char[]
length com parênteses na String, sem parênteses no array. É inconsistência da própria linguagem — não tente achar lógica, só decore.
